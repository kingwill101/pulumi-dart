# Generated Dart Packages

This directory contains Pulumi package schemas and generated Dart SDK projects.

Structure:

- `schemas/`: downloaded provider schemas (`*.schema.json`)
- `<provider>/`: generated Dart SDK package for that provider (for example `packages/gcp`)
- `analysis/`: `dart analyze` machine-format reports generated by Task targets

The temporary generation workspace is `.gen/sdk-gen` at the repo root.

Use the root `Taskfile.yml`:

```bash
task setup
task generate:gcp
task generate:gcp-global-cloudrun
task generate:google-native
task generate:aws
task generate:awsx
task generate:all

# Optional generation controls:
# - keep manually curated examples across regenerations (default true)
# - run dart format on generated package output (default true)
task generate:provider PACKAGE=aws PRESERVE_EXAMPLES=true FORMAT_GENERATED=true

# If you want to refresh generated examples from scratch:
task generate:provider PACKAGE=aws PRESERVE_EXAMPLES=false

# Fail generation if formatter finds parse errors (default is warning-only):
task generate:provider PACKAGE=aws STRICT_FORMAT=true

# Create a local smoke project wired to generated SDK path dependencies.
task smoke:init PACKAGE=gcp

# Optional: run preview in that smoke project.
task smoke:preview PACKAGE=gcp

# Run any custom command with smoke env setup.
task smoke:exec PACKAGE=gcp CMD='pulumi about'
task smoke:stack PACKAGE=gcp
task smoke:up PACKAGE=gcp

# Optional: override the default local passphrase for this run.
task smoke:preview PACKAGE=gcp DEFAULT_PULUMI_CONFIG_PASSPHRASE=my-passphrase
```

The smoke project is created under `.gen/smoke/<provider>` and is configured with:

- provider SDK as a `path` dependency (`packages/<provider>`)
- local core SDK override for `pulumi` (`pulumi-dart/`)

This is the recommended local testing path and avoids publishing to pub.dev.

If you already have a Pulumi Dart project and want to test a generated provider locally:

```bash
# Generate the provider SDK first.
task generate:provider PACKAGE=gcp

# Wire your existing project to local SDK paths.
task project:use-local-provider \
  PROJECT_DIR=/abs/path/to/your/pulumi-project \
  PACKAGE=gcp
```

This updates that project's `pubspec.yaml` to use:

- `pulumi_<provider>` from `packages/<provider>` via `path:`
- `pulumi` via `dependency_overrides` from local `pulumi-dart/`

So there is no local "publish" step required for provider smoke testing.

If you run preview manually, include local language host path and passphrase env:

```bash
cd .gen/smoke/gcp
export PATH="/abs/path/to/pulumi-dart/pulumi-language-dart:$PATH"
export PULUMI_CONFIG_PASSPHRASE="pulumi-dart-smoke"
pulumi stack select dev --create --non-interactive >/dev/null
pulumi preview --non-interactive
```

## Versioning Policy

- Generated package version defaults to the upstream provider schema version (`schema.version`).
  - Example: `random@4.19.1` schema -> generated `pulumi_random` package `version: 4.19.1`.
- This matches the versioning approach used by other Pulumi SDKs.
- For parameterized providers, plugin/parameterization metadata is still emitted separately in generated registration code; this package version policy does not remove that metadata.
- Generated `pubspec.yaml` also carries schema package metadata when present:
  - `description`
  - `license`
  - `homepage`
  - `repository`
  - `keywords` mapped to pubspec `topics`

Optional environment overrides:

```bash
# Hard override exact SDK version.
PULUMI_DART_SDK_VERSION=9.11.0-dev.2 task generate:provider PACKAGE=gcp

# Keep upstream base version and append suffix.
PULUMI_DART_SDK_VERSION_SUFFIX=dev.2 task generate:provider PACKAGE=gcp
```

## Why Not `build_runner` As The Core Generator

This generator is schema-driven and integrated with Pulumi's language-host flow (`pulumi package add` / `GeneratePackage`).
It produces full standalone SDK packages from provider schemas and needs Pulumi-specific packaging and runtime metadata behavior.
`build_runner` is useful for Dart source transforms inside an existing package, but it is not the primary fit for cross-provider SDK package generation.
